# 에러 응답 형식 (백엔드 공통)

> 모든 API 에러는 이 형태 하나로 통일한다. `GlobalExceptionHandler`(공통)가 만들어주는 형식이고,
> 각자 도메인의 `@RestControllerAdvice`(예: 지은의 `FileExceptionHandler`)도 이 모양만 지키면 된다.

## 기본 형태

```json
{
  "timestamp": "2026-09-14T21:10:00",
  "status": 400,
  "message": "사람이 읽을 에러 메시지"
}
```

검증 실패(`@Valid`)처럼 **필드별로** 원인을 알려줘야 할 때만 `errors`가 추가된다.

```json
{
  "timestamp": "2026-09-14T21:10:00",
  "status": 400,
  "message": "입력값이 올바르지 않습니다.",
  "errors": {
    "username": "3~30자여야 합니다.",
    "email": "이메일 형식이 아닙니다."
  }
}
```

## 상태 코드 매핑 (지금까지 쓰는 것)

| 상황 | 상태 코드 | 예 |
|---|---|---|
| 요청 값 검증 실패 (`@Valid`) | `400` | `MethodArgumentNotValidException` |
| 이미 있는 값 (이메일/아이디 중복 등) | `409` | `IllegalArgumentException` |
| 로그인 실패 (비번 틀림 등) | `401` | `BadCredentialsException` |
| 존재하지 않는 리소스 | `404` | `ResponseStatusException(NOT_FOUND, ...)` |
| 권한 없음 (남의 여행 등) | `403` | `ResponseStatusException(FORBIDDEN, ...)` |

## 새 도메인(파일 업로드 등)에서 커스텀 예외를 쓸 때

`GlobalExceptionHandler`에 핸들러를 추가해도 되고(공용 파일에 손대는 게 부담되면),
**자기 패키지에 별도 `@RestControllerAdvice`를 만들어도 된다** — 여러 개 있어도 서로 다른
예외 타입만 처리하면 충돌 없음. 다만 응답 JSON은 위 형태를 그대로 맞출 것.

```java
@RestControllerAdvice
public class FileExceptionHandler {

    @ExceptionHandler(FileUploadException.class)
    public ResponseEntity<Map<String, Object>> handle(FileUploadException e) {
        Map<String, Object> body = new LinkedHashMap<>();
        body.put("timestamp", LocalDateTime.now().toString());
        body.put("status", HttpStatus.BAD_REQUEST.value());
        body.put("message", e.getMessage());
        return ResponseEntity.badRequest().body(body);
    }
}
```

## `ResponseStatusException`도 같은 형태로 나간다

`throw new ResponseStatusException(HttpStatus.NOT_FOUND, "여행을 찾을 수 없습니다.")` 처럼
404/403 등에 흔히 쓰는 것도 `GlobalExceptionHandler`가 잡아서 위와 같은 형태로 바꿔준다.
따로 처리할 필요 없이 그냥 던지면 된다.
